# 重要决策

Last Updated: 2026-09-17。记录会影响后续工作的选择；“未采用”不等于“试验失败”。证据以当前代码与验证记录为准。

## D01 · 本地轻量工作台与真实引擎（2026-09-09）

- **背景/问题**：现有 SPPARKS 源码需要易于展示的交互界面，首要目标不是计算加速。
- **方案与选择**：当前采用原生 ES modules + Three.js、Python 标准库本地服务、已有 WSL 串行引擎。
- **原因/其他路线**：避免在演示验证阶段引入云后端、数据库和前端框架迁移；未记录对这些方案做过失败试验，不应捏造失败结论。
- **已验证**：三模型真实运行，原始 dump/日志与展示结果一致；自动检查见 VERIFICATION。
- **重考虑条件**：跨设备部署、多用户、持久实验、数据规模或团队维护需求实际出现。新增框架需要明确收益，不为美化局部 UI 重建项目。

## D02 · 真实帧与科学语义（2026-09-09；2026-09-14 扩展）

- **问题**：三维效果、配色和曲线容易造成错误的物理解释。
- **选择**：只显示真实输出帧；Potts 状态不当作独立晶粒；Ising 的此实现能量累计异向邻居，不套用负 Hamiltonian 标签；平均自旋为 `(N2-N1)/N`。
- **其他方案与原因**：不插值生成虚构组织，不把模型量直接标为实验秒/K/J。颜色按状态分类，不声称晶体真实取向。
- **已验证**：固定格点、递增时间、有限能量校验；真实随包结果一致性测试。Ising 随包末态能量 9,044，平均自旋约 −0.734（仅对应该基准）。
- **重考虑条件**：提供严格单位映射、参考解、晶粒定义或经过验证的插值/分析方法，并保持来源说明。

## D03 · 第三案例采用薄膜，烧结延后（2026-09-14）

- **背景**：用户选择烧结/薄膜方向；经典烧结原例缺少随包未分发的 CuO3 初始结构，历史核查为 38 MB、403×403×95 域。
- **方案**：取得烧结原数据；构建经验证的小尺寸烧结；使用资料齐全的薄膜例。
- **选择与原因**：先接入薄膜 `examples/thin_film_growth/in.thin_film.no.schwoebel` 的缩小算例，保留非线性 hop 势垒；不为凑案例虚构烧结初态。
- **语义边界**：薄膜保持原有二维三角晶格，允许视图操作但不能宣称三维薄膜体；默认隐藏空位/顶部层，统计占据数。原能量表为零，不能拿平坦能量曲线冒充生长指标。
- **已验证**：随包结果 1,536 格点、11 帧，占据数 96→487；原 dump 与 JSON 一致。
- **重考虑条件**：取得完整烧结数据或验证替代小例。多案例整体验收按用户要求延后，不影响三个现有模型已经实现的事实。

## D04 · 专业操作顺序优先于成果展厅布局（2026-09-17）

- **背景/问题**：用户明确指出原界面信息层级不足，要求先物理、后平台、再运行与可视化，目标是非 SPPARKS 专家也能理解输入。
- **方案**：只改配色/卡片；分步向导；单页分区工作台。
- **选择**：单页上左物理、上右平台，下方控制台与可视化；紧凑工程风格。保留展示模式和结果操作。
- **原因**：同屏查看输入与结果便于讲解和调整；分步向导不是主操作框架。旧大标题主导的展厅排布不再作为工作台布局依据。
- **已验证**：桌面与窄屏操作；用户明确新版工作台验收通过。CPU 核数等是宿主机信息，实际串行资源独立标注，不放无效资源配置。
- **重考虑条件**：新求解器确实支持并行/内存配额，或实际用户测试需要进一步分步化。

## D05 · 新手引导与任务不确定状态（2026-09-17）

- **问题**：新手不知道如何开始；加载失败、提交失败和任务查询断线容易被混为一谈。
- **选择**：页内可关闭四步引导，不自动改参数或运行；引导偏好用 localStorage。任务 ID 用 sessionStorage，但不声称任务已持久化。
- **其他路线与原因**：不以每次强制弹窗阻断老用户；不因网络超时自动再次 POST，不把提交状态未知说成确定未启动。已知任务断线保持输入锁定，显式重新查询同一 ID。
- **已验证**：14 项自动测试基线；页面错误参数阻止提交、实际 Potts 计算、服务断开后载入重试、引导偏好。实际求解器中途失联场景尚非完整覆盖。
- **重考虑条件**：后端实现幂等提交、任务列表/持久化后，可改进未知提交的恢复；需同步设计恢复语义。

## D06 · 仓库记忆与单一现行路线图（2026-09-17）

- **背景**：用户要求多阶段、多会话项目不依赖聊天恢复。
- **方案与选择**：根 AGENTS 约束工作方式；四个 Persistent Project Memory 文件分别保存未来、现在、原因、结构。用户随后明确要求删除旧 PROJECT_PLAN，现仅 PLAN 维护路线，旧记录从 Git 历史查阅。
- **原因/否决路线**：不用聊天逐轮流水账或两个独立现行计划；Task/checkpoint 是最小常规持久化单位，Phase 必做完整 reconciliation。
- **已验证**：初始化时核对源代码、Git 工作区及测试；当时工作台/引导未提交。随后用户验收引导并授权将所有更新和上下文一并提交推送；恢复时仍需检查 Git，而非假设工作区永远干净。
- **重考虑条件**：文档规模增长导致职责重叠时精简/归档；不降低代码/可验证结果优先级。用户要求不再创建 `COMMIT_MESSAGE.txt`，提交说明继续保存在 Git。

## 环境故障经验（既有会话观察，不作为通用架构决策）

- Git 推送曾受全局 `gh-proxy.org` URL rewrite 影响；当时使用仓库局部直连映射解决。复现连接问题先检查 `git config --show-origin --get-regexp '^url\.'` 和实际 remote，不能默认网络或凭据坏了；不要再次写入凭据或未经核对修改全局配置。本轮未重新验证远端连接。
- 原始 SPPARKS dump 可能带行尾空格；必要时把生成数据与手写代码的 whitespace 检查分开，保留原始资料可追溯性；不要为格式检查无理由重生成全部算例。
